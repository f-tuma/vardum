# Import a folder into a Vard

Use published **CLI 0.8.3** for folder import and the complete folder plan
below. Import was introduced in CLI 0.7.0 and is absent from CLI 0.6.0.
Verify the target backend before upgrading; see
[release evidence and upgrade order](client-release-0.8.3.md#upgrade-order) and
[npm release status](npm-release.md).
The server must advertise both `folderUploadResume: 1` and
`folderVardImport: 1` before using the new command. Deploy the matching server
with migrations through `0015_upload_request_checksum.sql` before upgrading
project clients. The consumption flow continues to use schema **2** frozen
snapshots.

Run the command from a project containing `vardum.json`. It uses the server,
workspace and Vard in that configuration. With a write key, preview the import:

```sh
vardum push-folder ./images brand/mobile/ --output images/ --dry-run
```

Then run the same command without `--dry-run`:

```sh
vardum push-folder ./images brand/mobile/ --output images/
```

`brand/mobile/` is the destination in the workspace asset library. `images/` is
the destination relative to the project root when consuming the Vard. Nested
source directories are preserved in project output paths; source filenames keep
their extension there. Asset names and newly created library keys omit the media
extension. Existing matching keys, including keys with extensions from older
imports, keep their identity and delivery URL.

The preview separates library `new`, `update` and `skip` from Vard mapping `add`
and `keep`. An unchanged library asset can still need a new Vard mapping.
`changed` counts the planned library operations and mapping additions; JSON also
reports the two groups separately.

Without `--output`, `push-folder` continues to update only the library. With it,
the import checks the complete prospective Vard, including folder-rule outputs,
before uploading. Unsafe paths, case/Unicode equivalents, conflicting destinations,
file/directory overlaps and more than 1,000 outputs are rejected. An already
invalid Vard needs repair in the editor first. This preview is not a reservation:
concurrent edits can still make final application fail.

## Complete folder plan (CLI 0.8.0)

The terminal plan summarizes **New**, **Update** and **Skip** totals and previews the first 15 source files. Use `--dry-run --json` for the complete per-file plan.
Library-only JSON adds an all-file `library` report alongside mutation `actions`.
Each row shows source-relative `source`, exact resulting `key`, `libraryAction`
(`new`, `update`, `skip`) and `applied`. Existing rows report the actual asset ID
and current ready version ID when available. New dry-run rows do not reserve
upload IDs. Skipped rows add no mutation action or change and keep
`applied: false`: no upload occurred. Pending uploads retain their original
new/update classification with `resumed: true`, phase and exact journal IDs.
This reporting is absent from the published CLI 0.7.0 library-only command.

The terminal confirmation uses the same captured checksum plan as JSON. Before
upload, the CLI revalidates source metadata, the pending journal, remote identity
and current version, including both stem and filename keys. Vard imports also
recheck the mapping plan. Changed files or a competing filename/stem identity
stop execution before upload and require a fresh plan. Unknown unfinished-upload
activity on an older server is marked `uncertain: true` in a read-only library
preview; mutations require the resume capability and complete identity metadata.

An existing extensionless manual key is reused directly. An existing matching
filename key is reported as preserved with its original identity. If both keys
exist, the command names both and stops before upload; it does not choose or
merge assets based on their stem or checksum. Both `brand/mobile` and
`brand/mobile/` select `brand/mobile/`.

New mappings follow the latest original and are read-only. Existing equivalent
manual mappings retain their IDs, pins, transforms and writable settings.
Equivalent outputs already generated by a folder rule stay generated. The import
does not change privacy or make assets writable. It adds mappings and does not
remove unrelated outputs; `--output` cannot be combined with `--delete`.

The command uploads sources and adds mappings. It does not download over local
files or advance `.vardum.lock`. After import, use the ordinary consumption flow:

```sh
vardum status
vardum pull
```

Review changed project files and commit `vardum.json` and `.vardum.lock` with the
project. If every mapped output already exists and matches, use
[lock-only adoption](guide/pull.md#existing-project-files) instead of downloading
over it. CI can then restore that exact snapshot with `vardum pull --frozen`.
An independently retained old snapshot still has its old membership and versions;
the server must retain the underlying assets, version files and delivery keys.

## Resume an interrupted import

Rerun the exact same command with the same files. The private local
`.vardum.push.pending.json` binds the original server, workspace, source directory,
library prefix, Vard and output prefix. It retains exact source versions and
mapping progress, including unchanged source files, until tracking is durably
saved. It contains no API key or signed upload URL. Keep it while recovering.

An interrupted import may already have uploaded library assets or added mappings.
In JSON, `applied: true` confirms completed work; `false` cannot rule out a remote
change whose response was lost. Replay checks the same upload versions and keeps
already added mappings. It does not create duplicate versions or mappings.

If another writer replaced a source's current version, removed an asset, changed
an already applied mapping or introduced a conflicting destination, recovery
stops with an error. Resolve the reported conflict instead of retargeting the
journal. Successful library uploads remain in the workspace if mapping application
fails; the mapping batch itself is atomic. Expired uploads and abandoned mutexes
follow the explicit recovery instructions in the CLI error and
[CLI README](../apps/cli/README.md).

## API integration

Both endpoints are workspace/Vard scoped:

- `POST /api/workspaces/:workspaceId/vards/:vardId/items/import-plan`: read-only
  preflight of `{ files: [{ assetId, key, outputPath, checksum, mimeType, size }] }`.
  The supplied UUID identifies an existing asset or a planned new asset. Results
  report the current ready `versionId`, library action and mapping action/ID.
- `POST /api/workspaces/:workspaceId/vards/:vardId/items/import`: the same files
  with their exact ready `versionId`. The server checks that every source is
  still current and its checksum/type/size/key match, resolves the latest output
  union and inserts only absent mappings. It returns `added` and `kept` counts
  plus confirmed mapping IDs. Replaying a completed request keeps the same rows.

Planning requires read and update permissions, plus create for new assets and
publish for uploads. Application requires read and update. An import cannot
grant itself broader key permissions.

Use this additive endpoint for imports. The legacy `PUT .../items` deliberately
replaces the complete manual list and can remove previously imported mappings.
The import endpoint does not make an old stale whole-list edit safe. Servers
advertising `vardEditRevision: 1` offer dedicated [guarded editor routes](vard-editor-concurrency.md).
An import invalidates a previously read editor definition when it adds manual
mappings, so a stale guarded save fails with 409 and keeps the imported mappings.
Legacy clients and routes remain unguarded; published MCP 0.3.0 still uses them.
MCP 0.4.2 uses the guarded routes and refuses legacy fallback. Read
`get_vard` first and pass its original revision as `expectedRevision` for update,
replacement or deletion. Replacement items retain their existing manual `id`
(or `null` for a new mapping) and explicitly copy literal `pinnedVersionId` to
nullable `versionId`. A structured `vard_revision_conflict` / 409 requires a
fresh read, review and reapplication of the intended edit. See the
[MCP guide](guide/mcp.md#guarded-editing).
